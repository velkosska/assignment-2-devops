## [1]. Backend language and framework
Date: 2026-09-30
Status: Decided
Context: Lend is one process with server-rendered pages and a single SQLite file. Startup has to be one command, bound to 0.0.0.0, configured only through PORT and DATA_DIR. Every layer of this app has to be explainable on paper.
Decision: Use Python with Flask, Jinja templates, and the standard-library sqlite3 module.
Alternatives considered: Django, rejected because its ORM, admin, and auth would sit unused on two small domains. FastAPI, rejected because the interface is HTML forms, so Flask's built-in template rendering is the smaller fit.
Consequences: Runtime dependencies stay at Flask. SQL stays visible in lend/db.py, and there is no second frontend process to deploy in Assignment 2.

## [2]. Catalog and loans stay separate domains
Date: 2026-09-30
Status: Decided
Context: Lend needs two feature domains that could become separate services later. Both use the same SQLite file, so the boundary has to live in the code.
Decision: Catalog owns writes to the tools table through lend/catalog.py. Loans will own members and loans. retire_tool may read loans only to refuse retiring a tool that is still out.
Alternatives considered: One module for tools and loans, rejected because Assignment 2 needs a seam to split. A status column on tools updated by both domains, rejected because a return and a catalog edit could disagree about whether the tool is available.
Consequences: lend/catalog.py does not create loans. Loans reads tools.retired through the shared database. It does not write the tools table.

## [3]. An open loan is returned_at IS NULL
Date: 2026-10-05
Status: Decided
Context: Catalog and loans share one SQLite file. A tool can be borrowed only once at a time, and a volunteer needs to see which open loans are past due without a second process.
Decision: loans.tool_id references tools.id and loans.member_id references members.id. The partial unique index one_open_loan_per_tool allows one row per tool where returned_at is null. is_overdue compares due_at with the current time when the loan list is read.
Alternatives considered: A status or overdue column updated from both domains, rejected because a return and a catalog edit could disagree. A scheduled job that marks loans overdue, rejected because that needs a second process.
Consequences: return_tool updates loans only. A tool is available again when its open loan row has returned_at set. Overdue is derived, not stored.

## [4]. Tests cover domain rules, not routes
Date: 2026-10-06
Status: Decided
Context: The assignment asks for at least 70% coverage of the core business logic in both domains. The route functions open a connection, call one domain function, and render a template.
Decision: tests/test_catalog.py and tests/test_loans.py call add_tool, retire_tool, borrow_tool, return_tool, and is_overdue on a temporary SQLite file. Coverage is measured with pytest --cov=lend.catalog --cov=lend.loans --cov-report=term-missing, which reported 96%.
Alternatives considered: Coverage of the whole lend package, including app.py, rejected because untested route functions would make the percentage describe templates more than rules. Tests through the Flask client, rejected because they would repeat the same rules through form parsing.
Consequences: A change to a borrow, return, retire, or overdue rule fails a test. A broken template can still pass this command.

## [5]. No reminder to the member
Date: 2026-10-08
Status: Decided
Context: A member who still has a tool after due_at needs to hear about it from the volunteer at the desk. Sending that reminder from the app would need a mailer and a schedule beside the one web process.
Decision: Do not email the member. The volunteer sees Overdue on the loans page, because list_open_loans calls is_overdue while it reads loans whose returned_at is null.
Alternatives considered: Emailing the member when due_at passes, rejected because it needs a mailer outside this process. A notifications table drained by a second worker, rejected because this assignment allows one process only.
Consequences: Nothing is sent when a loan becomes overdue. The loans page is the only place it shows, and only while that page is open. Whether overdue is stored is ADR-3, not this decision.
## [6]. The split: catalog and loans become two services
Date: 2026-11-10
Status: Decided
Context: Assignment 2 requires one service per feature domain, each with its own container and its own database, talking only over HTTP. ADR-2 already drew the seam: catalog writes `tools`, loans writes `members` and `loans`. In the monolith, two queries crossed that seam through the shared SQLite file. `borrow_tool` read `tools.retired`, and `retire_tool` read open rows in `loans`. The pages also joined `tools.name` onto loans.
Decision: Keep the ADR-2 seam. `services/catalog` owns `tools` in database `catalog`. `services/loans` owns `members` and `loans` in database `loans`. `loans.tool_id` becomes a plain INT with no foreign key. Both cross-seam reads become server-side HTTP calls. Borrow and repeat call `GET {CATALOG_URL}/tools/{id}`, and retire calls `GET {LOANS_URL}/loans?tool_id={id}`. Each call has a 2 second timeout. If the other service does not answer, the request returns 503 with a clear message and writes nothing, so it fails closed. Tool names on the loans and history pages are joined in the browser from `GET /tools`. If catalog is down, those rows show `Tool #id` with a notice instead.
Alternatives considered: Moving the retire rule into the UI, rejected because a second browser tab could still retire a tool that is out. Letting loans write a status column on `tools`, rejected for the same reason ADR-2 rejected it: two writers to one table. Caching the tool list in loans, rejected because a retired tool could be lent from a stale cache, and the cache would need a refresh process.
Consequences: The services call each other in both directions, so neither one can check its rules alone. There are two calls in total, which suggests the seam is in the right place. Integrity across the seam is checked at write time only. A tool retired in one moment and borrowed in the next can slip through, because the two checks are not one transaction. At one desk that race is accepted. `/health` reports only the service's own database, so a down neighbour does not make a healthy service look broken.

## [7]. Data and migrations: one database per service, numbered SQL files, forward only
Date: 2026-11-21
Status: Decided
Context: The monolith kept every table in one SQLite file and created the schema on first boot, which cannot change a table that already holds rows. ADR-6 gives each service its own SQL Server database, and on Azure each database is serverless and pauses when idle. Once those databases hold data, the schema has to change in place. The monolith's code had no seed data, so no rows were carried over: the tables moved by being created again, from the same definitions, in the database of the service that owns them. `tools` went to the catalog database, and `members` and `loans` to the loans database.
Decision: Each service keeps numbered SQL files in `services/<name>/migrations/` and applies them with its own runner, `migrate.py`, when it starts. The runner creates `schema_migrations` if it is missing, applies every file not recorded there in number order, and records each file in the same transaction that applied it. `GO` lines split a file into batches. A file that fails is rolled back whole and the service does not start. Applied files are never edited, and a correction is a new file. Migrations are written to be additive: a new nullable column or a new table first, a removal only later, once no running version needs the old shape. The deployment has one replica at most, so two copies never migrate at the same time. Migration 002 of the catalog adds `tools.retired_at` and gives the tools that were already retired their `created_at`, because the real date was never stored. That backfill is an approximation and the OpenAPI description says so. It ran on Azure over four existing tools and all four rows kept their values (`docs/evidence/migration-002.md`). The integrity lost at the seam is the foreign key from `loans.tool_id` to `tools.id`, which cannot exist across two databases. It is compensated in code: borrowing asks catalog whether the tool exists and is not retired before it writes, and fails closed if catalog does not answer (ADR-6). Tools are retired and never deleted, so an id that was valid stays valid. The partial unique index `one_open_loan_per_tool` still lives with the loans table, so one open loan per tool is enforced by the database itself. Recovery plan for a bad migration: there are no down migrations. If the migration fails, nothing is applied, the new revision never becomes healthy, the post-deploy check turns the run red, and the previous revision keeps serving. Because migrations are additive, that previous revision also still works if a migration did succeed and the code is what is wrong, so the fix is to deploy the earlier image by its commit SHA with `az containerapp update --image`. If a migration succeeded and is wrong, the fix is a new migration, deployed through the pipeline. If data was damaged, Azure SQL point-in-time restore creates a new database from its automatic backups, and the rows are copied back from it. The restored copy costs money while it exists, so it is deleted afterwards.
Alternatives considered: Alembic or Flyway, rejected because the schema is three tables and two files, and a runner of about forty lines is something I can explain line by line, where a tool adds a dependency and a vocabulary of its own. Creating tables with `IF NOT EXISTS` at boot, as the monolith did, rejected because it never changes a table that exists. Down migrations, rejected because forward-only is allowed and a down script that drops a column loses exactly the data a recovery needs. Running migrations from the pipeline before the deploy, rejected because the pipeline would need a database login and a firewall rule, which means waking a paused database from the runner, and the brief wants CI kept away from Azure SQL. Keeping a foreign key by sharing one database, rejected because it undoes the split.
Consequences: Migrations run on the first start after a deployment, so that first request is slower, and on Azure it already waits for the database to resume. A migration that locks a table would block requests, which is harmless at this size and would not be at 100 times the data. The `db_ddladmin` role is enough to run migrations and nothing more. Backfills can be approximations, as 002 is. Integrity across the seam is checked when a loan is written, not by the database, so a tool that is retired between the check and the insert can still be lent once, which ADR-6 accepts. Rolling back by image only works while migrations stay additive, and that is a rule to keep, not something the runner enforces.

## [8]. Serverless hosting on Azure: scale to zero, and what it does to the containers and the database
Date: 2026-11-21
Status: Decided
Context: The services have to run on Azure for Students with nothing that costs money while the app is idle, and the whole system has to be deployed by the pipeline from `main`. Idle is the normal state of a tool library, so the cost model matters more than the speed of the first request. Scale to zero has two effects on this system. A container that was removed has to start again, and the serverless database pauses after a fixed 60 minutes without connections, so the first request after a quiet period may find both asleep.
Decision: Everything is in one resource group, `rg-mvelkoska`, and named with the prefix `mvelkoska`. The two services are Azure Container Apps on the Consumption plan (0.25 vCPU and 0.5 GiB each, external HTTPS ingress on port 8000, minimum 0 and maximum 1 replica), in one Container Apps environment, which also creates its Log Analytics workspace. I keep it, because it is where the container logs go. Billing is per second of vCPU and memory while a replica runs, plus requests, after a monthly free allowance, so an idle service costs nothing. The databases are two Azure SQL serverless databases on the free offer (General Purpose, Gen5, 0.5 to 1 vCore, locally redundant backups) on one SQL server. They pause when idle, and when the monthly free compute is used up they pause instead of billing (`AutoPause`). The UI is a storage account with the static website feature, billed per gigabyte stored and per operation. It replaces the Static Web App of the first version of the brief, because the course guide for Azure for Students changed the target and gave the storage account's web address as the public address and the only origin the services accept. The images are public in GHCR, which is free and lets Azure pull them without a credential. The pipeline signs in with OpenID Connect as a managed identity that is Contributor on the resource group only, so no Azure password exists. Nothing in the system has a fixed monthly cost. For the cold start the services connect to the database with retries and a growing wait (1, 2, 4, 8 and then 16 seconds, ten attempts, about 95 seconds in total), longer than a database takes to resume. `/health` makes one attempt and answers 503 at once, so a probe never waits. Migrations run in `migrate.py` before gunicorn starts, so the first request after a deployment waits for them as well, and with at most one replica they never run twice at the same time. The UI waits up to 35 seconds per attempt, tries a read three times and shows "starting up" while it waits, because Azure answers the first request with `503 App port is not ready` after about 30 seconds, without CORS headers, which the browser reports as a failed fetch. The calls between the services have a 10 second timeout on Azure (2 seconds locally), so a neighbour that is waking up is waited for. The infrastructure is created once by `infra/setup.sh` with Azure CLI commands that check before they create, and the pipeline then only updates the two apps and uploads the UI.
Alternatives considered: Always-on containers (minimum 1 replica), rejected because it costs money all day for a desk that is used a few hours a week, and cold starts are acceptable when the UI says what is happening. Bicep or Terraform, rejected because the system is three kinds of resource that are created once and then only updated, and a script I can read line by line is something I can explain, where infrastructure code would be one more language and one more state to understand. A Static Web App for the UI, rejected because the guide moved to a storage account. Azure Container Registry, rejected because it has a fixed monthly cost and GHCR is free. A service principal with a secret in GitHub, rejected because a federated identity has no secret to leak. Provisioned Azure SQL or a database with auto-pause turned off, rejected because they have a fixed monthly cost. A keep-warm ping from the pipeline or a timer, rejected because it would wake the database and cost money to hide a delay that the UI already explains.
Consequences: The first request after a quiet period is slow. I measured 13 seconds for catalog and 5 seconds for loans on 2026-11-21 when both containers were asleep, and the guide says a paused database adds up to about a minute. A request that arrives while the database resumes can fail with error 40613 and is retried, so a user sees a banner instead of an error. A deployment starts a new revision, so the first start after it runs the migrations, and the post-deploy check waits up to 10 minutes for both services to answer on the new commit. Every connection to Azure SQL wakes the database, so CI never connects to it. At 100 times the traffic this design changes in several places. The services would need a minimum of one replica, which ends the scale to zero and the cold start. More than one replica needs the migrations to run once before the replicas scale out, in a separate step or behind a database lock, because the single replica was what made running them at startup safe. The database needs a fixed vCore range without auto-pause, and the services need a connection pool, because each request now opens its own connection. The UI would go behind a CDN, the calls between the services would need retries and a circuit breaker rather than one timeout, and the infrastructure would move to code, so that more than one environment can be created the same way.

## [9]. Pipeline and testing: what CI gates on, and a cross-seam test on the real stack
Date: 2026-11-18
Status: Decided
Context: Assignment 2 needs every push tested and every image built, and images published only from main. ADR-4 chose domain-rule tests for the monolith. With two services, the risky part is no longer a rule inside one service. It is the two HTTP calls across the seam and what happens when one side is down. A stub of the other service tests our own code, but it cannot show that the real services agree on URLs and JSON, or that a stopped container produces a clean error.
Decision: CI runs three gates on every push and pull request, and images are built only after all of them pass. First, per service: ruff lint and format, validation of `openapi.yaml` with openapi-spec-validator, and pytest against a throwaway SQL Server container with coverage that fails below 70% (`fail_under = 70` in each `pyproject.toml`). A test in each service also compares the routes in the code with the paths in `openapi.yaml`, so the document cannot drift. Second, one integration job starts the whole compose stack with random database passwords that are generated in the job and masked, then runs `tests/integration/test_seam.py` over HTTP. It lends a tool and checks that catalog refuses to retire it because loans says it is out, then checks that loans refuses to lend it once catalog says it is retired. It stops catalog with `docker compose stop` and checks that borrowing answers 503 in under 10 seconds, writes nothing, and that loans stays healthy. It does the same for loans and retiring. Each test restarts what it stopped. Third, the `images` job builds both images, always. It logs in to GHCR and pushes only on a push to main, tagged with the commit SHA and latest. The unit tests of loans and catalog still replace the other service with a small function, because they are fast and exact about each status code. CI never connects to Azure SQL.
Alternatives considered: Stubs only, rejected because a stub can keep passing after the real service changes its URL or JSON, and it cannot test a stopped container. Contract testing with a tool such as Pact, rejected because it adds a tool and a broker for two services with two calls, and the OpenAPI documents already describe both sides. Running the integration test against Azure, rejected because every connection wakes the serverless database and costs money, and the brief forbids it. Putting the passwords in GitHub secrets for the test database, rejected because a throwaway database does not need a long-lived secret.
Consequences: A change to a status code, a URL, a timeout or the OpenAPI document fails CI before an image is published. The integration job needs several minutes because it builds both images and waits for SQL Server, and it would fail if SQL Server were very slow, so the test waits up to 150 seconds for both `/health` endpoints. Not tested on purpose: the JavaScript in `ui/` (there are no browser tests), the deployment on Azure and scale to zero, the retries against a paused Azure SQL database (error 40613), and the race where a tool is retired and borrowed at almost the same moment, which ADR-6 accepts. These are checked by hand after a deployment, with the health check in the pipeline as the only automatic signal.
